Training first, then add modules. These four carry most of the audit value of a QMS. Every
later module reuses their workflow, signature and audit services.

Shared workflow engine and step-up e-signatures
Document Control with templates, versioning, manifest page, watermarks

Email and in-app notifications through the automation engine, with default rules
My Work home

System architecture
All three clients call one API. The API is the only component that changes records,
checks permissions or records signatures. Anything slow or external runs in workers
that read the outbox, so an integration outage never blocks a user.
Reading the picture:
The API sends users to Entra ID for sign-in and for the step-up check before signing.
The API writes records, workflow state, audit entries and outbox events to
PostgreSQL in one transaction.
Workers pick up outbox events. They send notifications, call Graph, Teams, DocuSign
and push, and write audit checkpoints to the immutable anchor.

Workflow engine and e-signatures
One engine drives every module. Every transition runs in a single database transaction
that writes the state change, the audit entry and the outbox events together, or none
of them.
The document lifecycle is the first workflow definition shipped. Change Requests, Quality
Events and CAPA use the same engine with their own states.
Workflow definitions:
Stored as versioned JSON. A new definition version needs Quality Manager approval
before it goes live. Running instances keep the version they started on.
Each transition declares:
the roles allowed to take it
required fields
signature meaning (for example "Approved" or "Reviewed")
SoD rule (for example "author cannot approve")
SLA timer
Stages route parallel (all assignees at once, with a completion rule of all or N) or
sequential (ordered list).
Guards are evaluated in the API, never in the client.
An SoD override needs a named admin, a reason and a signature, and is logged as its
own audit event.

1. The user clicks Sign, or Sign all on a listed batch. The API records a signing intent: the
time, the signer and the exact record versions.
2. The API answers with a claims challenge for an Entra authentication context (for
example c1 ). A Conditional Access policy tied to c1 requires MFA.
3. The client signs in again with OIDC prompt=login , so a fresh sign-in happens every
time, then retries with the new token.
4. The API accepts the token only if acrs contains c1 and auth_time is later than the
signing intent. An older sign-in is refused, however recent.
5. The API writes one immutable Signature row per record: signer, meaning, signature
statement, UTC time, record version id, SHA-256 hash of the signed content.
This replaces the earlier 5-minute window, which let one sign-in cover any signature made
in those 5 minutes. Each signing action now needs its own fresh sign-in, as the prompt
requires. Entra authentication context and claims challenges are documented by
Microsoft (developer guide). Microsoft has also announced a Conditional Access "sign-in
frequency: every time" option for authentication contexts. Its current status and browser
behaviour are not confirmed, so the plan does not rely on it: the API's auth_time check is
the control. Verify with IT that prompt=login works together with the claims challenge.
Signature integrity:
Signature rows cannot be updated or deleted. The app's database role has insert-only
rights on them.
Each signature references an approved, immutable DocumentVersion.
The manifest page is rendered from these rows, not typed.
Automation and notifications
Nothing is sent from request code. Every event goes into an outbox row in the same
transaction as the change. Workers then turn outbox rows into rule runs and
notifications. So no notification goes out for a change that rolled back, and none is lost for
a change that saved.
Pipeline:
1. Outbox. Each transition, assignment or due-date event writes an outbox_event row
with the record, the event type and the actor.

Security architecture and Annex A support
The audit trail is built to be tamper-evident, not tamper-proof. A cloud or database
super-admin can always change rows. The design makes any change detectable and
keeps those super-admin powers behind break-glass access that is itself logged.
How the audit log works:
1. Each AuditLogEntry stores hash = SHA-256(prev_hash ||
canonical_json(entry)) , chained per tenant. Entries are serialised with one fixed
canonical JSON scheme (RFC 8785 proposed; verify), so the verifier rebuilds exactly
the same bytes.
2. The writing transaction takes a per-tenant lock ( pg_advisory_xact_lock ) before it
reads the previous hash. Two saves at the same moment queue instead of splitting
the chain. Load tests check the queue stays short at the agreed concurrency.
3. Logged events: every create, update, delete, signature, permission change, login,
export and read of a Restricted record, with user, UTC time, before and after values, IP
and device.
4. The app's database role can only insert into the audit table. No update or delete
grants exist for it.
5. Every 15 minutes (proposed), a job writes the latest chain hash and entry count to a
Blob container under a time-based immutability (WORM) policy. Nobody in the app
can change that container, including its admins.
6. An hourly verifier checks every entry since the last anchor, and a nightly run
recomputes the whole chain. A mismatch raises a security incident alert.
7. Database admin and cloud owner roles are break-glass only: time-boxed, with
approval and alerting.

Mobile
The mobile app is a thin client over the same API. It holds no business rules and keeps as
little on the device as possible. Its scope is the one in the prompt: My Work, push, review
and sign, read and train, raise observations offline, view CR and CAPA status.
Sign-in. Entra ID through the system browser (MSAL or an OIDC library; verify current
Expo support). Biometrics only unlock a locally stored session. Signing still goes
through the step-up challenge.
Storage. Tokens in the OS keychain or keystore. Documents are streamed for viewing
and not saved. Offline observation drafts and photos are encrypted with a key held in
secure storage. All of it is wiped on logout or when the server revokes the session.
Push. Payloads carry only an id and a generic line ("You have an approval waiting").
The app fetches details after unlock.
